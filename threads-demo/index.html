E se tirassem
a trava?

Python 3.13+ tem um build sem o GIL. O mesmo código, outra história.

  • Build sem GIL desde o 3.13. No 3.13 era experimental; do 3.14 em diante é oficialmente suportado.
  • O mesmo ThreadPoolExecutor, sem o GIL, passa a ocupar vários núcleos.
  • Ainda não é o default. Bibliotecas em C podem ter atrito — essa demo usa só a stdlib.
import sys
sys._is_gil_enabled()  # → False
$ .\.venv-ft\Scripts\python.exe src\main.py cpu --upto 800000 --workers 4
</> UPDATES_2026.py print("onde estamos")

Free-threaded em 2026.

  • 3.13 (out/2024) — build sem GIL entra, experimental (PEP 703, fase I).
  • 3.14 (out/2025) — deixa de ser experimental, vira oficialmente suportado (PEP 779, fase II). Ainda opcional.
  • 3.15 (out/2026) — Stable ABI abi3t pra free-threaded; macOS instala por padrão.
  • Ainda não é o default — fase III indecidida, depende do ecossistema de extensões C.

No CEP, free-threaded não dá ganho extra — o gargalo é a rede, não a CPU. No carimbo, free-threaded faz as threads acelerarem de verdade.

</> RESUMO.py print("leve isso pra casa")

Três ideias.

  • I/O-bound → threads já ajudam hoje.
  • CPU-bound + GIL → o ThreadPool fica num núcleo só; processos usam os outros.
  • Free-threaded → o mesmo ThreadPool finalmente ocupa vários núcleos.

Regra de bolso: com o GIL, thread não espalha em núcleos — processo sim. Sem o GIL, thread também espalha.
